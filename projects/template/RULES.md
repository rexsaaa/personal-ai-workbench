# 工作区协作规则

## 核心作用

定义需要协调工作区多个模块的通用协作流程。

## 通用规则

### 项目上下文维护

周收口日和月收口日，在生成后续计划前按以下顺序维护项目上下文；周中出现会影响后续工作的重大变化时及时处理。

- **复核项目定义**：结合现有 `PROJECT.md`、适用 Journal、实际结果和用户已经确认的决定，检查项目目标、完成标准、范围、持续约束及项目仓库信息是否仍然准确。项目定义仍较模糊时，判断本周期实践是否已经形成可确认的新认识；只有出现已确认的实质变化或澄清时才更新，不因普通进展反复改写。
- **复核当前状态**：以更新后的 `PROJECT.md` 为依据，结合现有 `CURRENT.md`、适用 Journal 和已经确认的实际结果，检查当前阶段、关键成果和持续阻塞是否仍然准确；Task 只作为计划对照。仅在当前状态发生实质变化时更新，普通推进不写入。
- **保持上下文一致**：更新时保留两份文档的当前有效内容，不追加周期报告或复制 Journal 过程；完成维护后再生成后续计划。

### 每日 Git 收口

- **触发条件**：用户明确表示结束今日工作。
- **执行顺序**：先确认当日收口安排要求的 Journal 和后续 Task 计划是否已经完成；未完成时先按各自规则完成，再检查并提交工作区 Git 变更。
- **提交范围**：只提交本次工作产生的项目管理文件变更，不纳入 `repository/` 或其他无关变更；没有变更时不创建空提交。
- **提交格式**：使用 `<YYYY-MM-DD>: <当日简要结果>`。
